# Pull Request Stack Creator

Turn one large change into a **stack**: an ordered chain of pull requests where
the bottom PR targets the trunk (usually `main`) and each PR above it targets
the branch below. Reviewers see only that layer's diff, and layers merge bottom
up.

This skill produces **three deliverables**:

1.  **One HTML page for the whole stack** — a single interactive explanation of
    the change end to end, with a short section summarizing each layer.
2.  **A stack** — real branches, in dependency order, tracked by `gh stack`.
3.  **Per-layer text** — a PR title and body for every layer, each grounded in
    that layer's own diff, generated by the `pr-description-creator` skill.

**The order is deliberate.** The page comes first because it is the analysis
pass. Writing an end-to-end explanation forces you to trace what depends on
what — and that dependency graph *is* the stack. A decomposition proposed
before that investigation is guesswork over filenames; one proposed after it
reflects how the code actually fits together. Explain first, slice second.

## Scope — read this first

Unlike `pr-description-creator`, **this skill does perform git and GitHub write
operations.** That is its purpose. But writes are tiered, and the tiers are not
negotiable:

| Tier | Operations | Rule |
|---|---|---|
| **Free** | `git status/log/diff/show/branch`, `gh stack view --json`, `gh pr view`, creating *local* branches from an approved plan | Run without asking |
| **Confirm first** | `gh stack submit`, `gh stack push`, `gh pr edit`, `gh stack sync`, `gh stack rebase`, `gh stack modify` | State exactly what will be pushed or opened, then wait for a yes |
| **Never unprompted** | `gh stack merge`, `gh stack unstack`, `git push --force*` outside `gh stack`, `git reset --hard`, deleting branches | Only on an explicit, unambiguous request |

Pushing branches and opening PRs is **outward-facing and hard to undo** —
teammates get notified, CI fires, review requests go out. One confirmation
covers one `submit`; it does not pre-authorize the next one.

## Constraints of stacked PRs (from GitHub's docs)

- Every branch in a stack must live in **the same repository** — cross-fork
  stacks are not supported.
- The trunk is usually the default branch but can be any branch (e.g. a release
  branch); pass it with `gh stack init --base <branch>`.
- **Dependency rule**: if code in one layer depends on code in another, the
  dependency must be in the same branch or a *lower* one. This is the single
  constraint that governs the whole decomposition.
- Stacked PRs are unavailable in GitHub Desktop, and the feature is in public
  preview.

## Workflow

### 1. Establish ground truth

- `gh auth status` — a stack needs an authenticated `gh`. If it is not, stop
  and say so; do not attempt to log the user in.
- `gh extension list` — confirm `github/gh-stack` is present. If it is missing,
  stop and tell the user to run `gh extension install github/gh-stack`; do not
  install it yourself.
- Trunk branch, **without hitting the network**:
  `git symbolic-ref --short refs/remotes/origin/HEAD` (→ `origin/main`).
  Fall back to `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`.
  Never use `git remote show origin` — it is a network round-trip that fails
  offline.
- `git fetch origin <trunk>` so the merge base is real. A stale local trunk
  silently pulls other people's merged commits into your layer diffs.
- `git status --porcelain` — if the tree is dirty, **stop and report it**.
  Branch surgery on a dirty tree loses work. Let the user commit or stash.
- `gh stack view --json` — if a stack already exists here, you are extending or
  re-describing it, not creating one: run step 3 scoped to the existing stack,
  then skip straight to step 6. This command **exits non-zero when the current
  branch is not part of a stack** — that is the normal "no stack yet" answer,
  not a failure. Do not report it as an error.
- `gh repo view --json isFork,nameWithOwner` — stacks cannot span a fork and its
  upstream. If this is a fork, every layer branch must live in it and the PRs
  must target a trunk in the same repository; if the user expects to open PRs
  against the upstream, stop and say a stack will not work there.
- **Degenerate cases**, checked before any planning:
  - The current branch *is* the trunk → there is nothing to slice. Ask which
    branch holds the work, or offer to build the stack forward from trunk
    (`gh stack init` then `gh stack add` per layer).
  - No commits ahead of the trunk → nothing to stack. Say so and stop.
  - Only one cohesive commit or a handful of files → say plainly that this does
    not warrant a stack and recommend `pr-description-creator` for a single PR.
    A one-layer stack is not a stack.

### 2. Survey the change

Enough to scope the explanation — the deep reading happens in step 3.

- `git log --oneline origin/<trunk>..HEAD` — the commits available to split.
- `git diff origin/<trunk>...HEAD --stat` **first**. Only then read the diff of
  the files that matter. Do not `git diff` a thousand-line change into context
  in one shot — sample the significant files and say what you sampled.

### 3. Explain the whole change first — one HTML page

Before proposing any slicing, run the `explain-diff-html` skill **once**, over
the entire change. This is the research step: it is what tells you which parts
of the change depend on which, and therefore what the layers should be.

Scope it to the whole change, not to layers that do not exist yet:

> Explain the change on `<current-branch>` compared to `origin/<trunk>`
> (`origin/<trunk>...HEAD`). This change is going to be split into a stack of
> dependent pull requests, so pay particular attention to **what depends on
> what**: imports, new symbols and their callers, schema before usage,
> interface before implementation. In the Code section, group the change into
> candidate layers in dependency order — foundations first, callers last —
> and for each one say what it contains and what it needs from below.

If a stack already exists here (step 1), scope the page to
`origin/<trunk>...<top-layer>` instead and have it describe the real layers.

Follow that skill's own rules: one self-contained HTML file, no external
assets, written **outside the repository** (use the session scratchpad
directory).

**Carry the findings into step 4.** The candidate layers the page identifies
are the raw material for the decomposition proposal — refine them, don't
re-derive them from scratch.

If the skill is unavailable or the run fails, say so plainly, work out the
dependency graph by reading the code yourself, and carry on — a failed page
never blocks the stack. Do **not** stop once the page exists; it is the input
to everything below it.

### 4. Propose the decomposition — then stop

Present a numbered plan, bottom to top, and **wait for approval before creating
any branch.** For each layer give: branch name, one-line purpose, the files it
carries, and why it must sit at that height.

Good layer boundaries, roughly in order of preference:

- **Bottom**: types, schemas, config, pure helpers — things with no dependencies.
- **Middle**: the core logic that uses them.
- **Top**: wiring, UI, docs, and anything that merely calls the layers below.

Rules for a sound stack:

- Every layer must **build and pass tests on its own**. A layer that only
  compiles once the layer above lands is misplaced — merge it down.
- Prefer 2–5 layers. One layer is not a stack; more than ~6 costs more to
  rebase than it saves in review.
- A layer that cannot be described in one sentence is doing two things.
- Name branches with a shared prefix and an order hint, e.g.
  `feat/auth-1-schema`, `feat/auth-2-service`, `feat/auth-3-routes`.

### 5. Build the stack

**Case A — the branches already exist** (bottom to top). Adopt them:

```bash
gh stack init feat/auth-1-schema feat/auth-2-service feat/auth-3-routes
gh stack view --short
```

**Case B — splitting one branch.** Keep the original branch untouched as a
safety net; it is your undo. Cut layer branches at commit boundaries, then adopt:

```bash
git branch feat/auth-1-schema  <sha-of-last-schema-commit>
git branch feat/auth-2-service <sha-of-last-service-commit>
git branch feat/auth-3-routes  <sha-of-tip>
gh stack init feat/auth-1-schema feat/auth-2-service feat/auth-3-routes
```

If the commits do not fall on clean boundaries, build the layers forward
instead — `gh stack init --base <trunk> <first-layer>`, apply that layer's
changes, commit, then `gh stack add <next-layer>` for each subsequent layer
(`-Am "msg"` stages and commits in one step). Cherry-picking from the original
branch is fine; rewriting it is not.

**Verify before going further**: check out each layer and run the repo's own
build/test gate (see step 8). A layer that fails in isolation must be
restructured now, with `gh stack modify`, not after the PRs are open.

### 6. Write the per-layer descriptions

For **each layer, bottom to top**, invoke the `pr-description-creator` skill
with the `Skill` tool, passing that layer's real range explicitly:

> Write the PR description for branch `<layer>` in this stack. The base branch
> for this PR is `<parent>` — scope every command to `<parent>...<layer>`, not
> `main...HEAD`. This is layer N of M in a stacked PR; the layers below it are
> `<...>` and may be assumed to exist.

This matters: a layer's reviewable diff is `parent...layer`. Scoped to
`main...HEAD` it would restate everything below it and the description would be
wrong.

**Ask for the text only.** `pr-description-creator` normally *begins* by
generating an HTML page of its own as its research pass, which would leave you
with one page per layer. It does not need to here — step 3 already did that
research for the whole change. Tell it so, in the same invocation:

> Produce the title and body only — skip your own step 2, the HTML explanation.
> The stack has already generated one combined page for the whole change at
> `<path>`; read it for context instead of building your own.

If it generates one anyway, discard it and report the path so the user can
delete it.

Then add stack context to the top of each body, so a reviewer landing cold knows
where they are:

```markdown
> **Stack** — layer 2 of 3 · base `feat/auth-1-schema`
> 1. #101 `feat/auth-1-schema` — add the user schema
> 2. **#102 `feat/auth-2-service`** ← you are here
> 3. #103 `feat/auth-3-routes` — expose the endpoints
```

PR numbers do not exist until step 9, so write this list with branch names first
and fill in the numbers when the PRs are created.

Save each body to its own file in the scratchpad directory (not the repo):
`pr-body-<layer>.md`.

### 7. Reconcile the page with the stack you built

The page from step 3 described *candidate* layers. Once the real stack exists,
check that it still matches:

- If the approved decomposition follows the page's grouping — the normal case,
  since the plan came from the page — just confirm the branch names it uses are
  the real ones, and you are done.
- If the layering shifted materially during step 4 or 5 (layers folded,
  reordered, split again), re-run `explain-diff-html` once over
  `origin/<trunk>...<top-layer>`, asking for one short subsection per real
  layer in stack order — branch, base, what it adds, why it sits there.

Do not regenerate the page for cosmetic differences. It is an expensive step,
and one accurate page beats two near-identical ones.

### 8. Verification status

Find the repo's actual gate rather than assuming a toolchain: `CLAUDE.md`,
`AGENTS.md`, `CONTRIBUTING.md`, or the README state it explicitly and that
statement wins. Otherwise infer it from `Makefile` targets, `package.json`
scripts, `pyproject.toml`, a Maven/Gradle build, or `.github/workflows/`.

Run it **per layer**, on that layer's checkout — that is the whole point of a
stack. Report real results. If you did not run it, say verification is pending
and leave the checklist boxes unchecked.

### 9. Submit — only after explicit confirmation

`gh stack submit` opens an **interactive TUI** that an agent cannot drive, so
always pass `--auto`. With `--auto`, PRs are created as **drafts** with
auto-generated titles unless you pass `--open`.

Show the user exactly what is about to happen — every branch that will be
pushed, every PR that will be opened, and the target repo — and wait.

```bash
gh stack submit --auto          # push all branches, open draft PRs, build the Stack Map
gh stack view --json            # capture the PR number for each layer
```

Then apply the real titles and bodies from step 6:

```bash
gh pr edit <n> --title "<layer title>" --body-file <scratchpad>/pr-body-<layer>.md
```

Update the stack-context block in each body with the now-known PR numbers.
Leave the PRs as drafts unless the user asks for them to be ready — a stack of
drafts is easy to fix, a stack of live review requests is not. Mark them ready
with `gh stack submit --open` or `gh pr ready <n>` when they say so.

### 10. Deliver

Close with, in this order:

- the stack, bottom to top: layer number, branch, base, PR number and URL;
- each layer's title, and the path to its body file;
- the path to the single stack HTML explanation;
- the verification result per layer;
- what is left for the user: PRs still in draft, layers that did not pass, and
  the merge path — bottom PR first, then `gh stack sync` to rebase the rest,
  or `gh stack merge` to merge the stack atomically **when they ask for it**.

## Maintaining a stack

Once the stack is open, the user will need these — run them only on request,
and only from the confirm-first tier:

- `gh stack sync` — fetch, cascade-rebase every layer onto its updated parent,
  push atomically with `--force-with-lease`, and relink the stack on GitHub. Run
  this after the trunk moves or after any layer is merged. Add `--prune` to drop
  local branches for merged PRs. It will not open PRs; that is `submit`.
- `gh stack rebase` — for when `sync` reports conflicts. Resolve, then
  `gh stack rebase --continue`, or `--abort` to restore every branch.
- `gh stack modify` — interactive TUI to reorder, fold, drop, insert, or rename
  layers. Cannot be driven by an agent; hand it to the user, and note that
  `gh stack submit` must follow to update GitHub.
- **After any layer changes**, its description may be stale — re-run step 6 for
  the affected layer, `gh pr edit` it, and regenerate the stack page (step 7) if
  the shape of the stack changed.

## Principles

- **Explain before slicing.** The page is the research, not a souvenir. The
  dependency graph it uncovers is what determines the layers.
- **Plan before branching.** The decomposition is the hard part and the user's
  call. Never create branches from a plan they have not seen.
- **Every layer stands alone.** Builds, tests, and reads as a coherent change by
  itself. If it doesn't, the boundary is wrong.
- **Each description describes its own layer.** Scoped `parent...layer`, never
  the whole stack.
- **Push and publish only on a yes.** Local work is cheap to undo; a stack of
  open PRs is not.
- **Grounded.** Every claim in every description comes from that layer's diff,
  its commits, or the user — never from guesswork.
- **The original branch survives** until the user says the stack is good.
